# Job prompt template

Fill every placeholder. The agent starts cold and this is all it knows.

---

You are implementing one phase of the `<slug>` feature. Work only on this phase.

**Start on the feature branch**

You are in your own git worktree. The feature's work lives on `feature/<slug>`, and the
branch you are standing on is not it. Before you read or build anything:

```bash
git fetch origin
git switch -C <slug>-phase-<n> origin/feature/<slug>
```

`-C` creates that branch or resets it, so the same command is right whether this worktree
is new or has already done a phase. Everything you build goes on it. Skip this and you will
rebuild what an earlier phase already did.

**Say what you are on the sidebar**

A person watching the sidebar sees one row per session. Call `mcp__orchestrator__set_status`
before you start reading:

```
mcp__orchestrator__set_status({
  icon: "🔧",
  title: "<slug> phase <n>",
  role: "Implementer",
  task_icon: "📖",
  task: "reading the plan"
})
```

Then call it again with `task` alone as the work moves — "building", "running the proof",
"writing the report", "PR open", "blocked, asked the orchestrator". A call naming only `task`
keeps the name and the role you set here. Keep it to a few words; the row gives it one line
and cuts a long one. Nothing else tells the person watching what this session is on.

**Read first**

- `docs/plans/<slug>.md` — the plan. Your phase is **Phase <n>**.
- `docs/plans/memory/<slug>.md` — the feature memory. Facts every session on this feature
  shares. You do not edit this file; see "Report" below.
- <any file the phase depends on: a design document, a previous phase's report>

**What to build**

<the phase's "What it builds", quoted from the plan>

**Proof**

<the phase's proof, quoted from the plan>. Run it and say what it said.

**Out of scope**

<the phase's "Out of scope for this phase", plus anything from the plan's "Not building"
that this phase sits next to>

Something you find that needs doing but is not in this phase goes in your report, or in
`docs/issues/open/` if it is a problem rather than an idea. Do not build it.

**Finish with a PR**

Commit your work, push your branch, and open a pull request into the feature branch:

```bash
git push -u origin <your branch>
gh pr create --base feature/<slug> --title "<slug> phase <n>: <what>" --body "<what you built, and what the proof printed>"
```

The orchestrator reads the diff, merges it, and then releases this session, which removes
the worktree. This phase is the whole of your job; the next one goes to a session that does
not exist yet. Leave nothing uncommitted — the removal stops over uncommitted changes, and
work you did not push is work the next phase cannot see. Commit the report below on the same
branch, so it arrives with the PR.

If the push is rejected or the PR shows a conflict, the feature branch moved under you:
`git fetch origin && git rebase origin/feature/<slug>`, resolve it, and force-push.

**Report**

When the work is done, write `docs/plans/reports/<slug>/<yyyy-mm-dd>-phase-<n>-<what>.md`
following `docs/plans/README.md`, with these headings:

- **What was built**
- **What was verified, and how** — the proof, and what it printed
- **What was left undone** — deferred work, and why
- **Bugs found and not fixed**
- **Mechanical friction** — flaky or slow tests, slow builds, anything that cost time
  without being about the feature
- **Memory suggestions** — what you would add to the feature memory, and why the next
  phase would otherwise rediscover it. Schema that settled differently from the plan,
  invariants that turned out to matter, files whose importance was not obvious. No code,
  and nothing about what you did — that is the rest of this report. The next phase runs in
  a session that has none of your context, so anything it needs and cannot read off the
  branch has to come through here.

**Work unattended**

Nobody is watching this session, and you have no tool for asking a user anything — the spawn
removed it. Bias toward working without stopping for clarifying questions. The plan has settled
the big decisions. When you would normally pause to check, make the reasonable call, keep
going, and say what you decided in your report. When you are genuinely blocked, message the
orchestrator, which is the one thing that can answer you.

**Talking to the orchestrator**

The session that started you is the orchestrator, and you can message it at any point.
Call `mcp__orchestrator__list_sessions`, find your own row, and take its `parent_id` — that
is the one to write to. Then `mcp__orchestrator__send_message`.

Message it as soon as you are stuck. It holds the whole plan, you hold one phase, and the
thing blocking you is usually something it can answer in a sentence or decide on your behalf.
Worth a message:

- The plan tells you to build against something that is not there, or that works differently
  from how the plan describes it.
- A dependency you were told had landed has not.
- The proof cannot be run as written, or fails for a reason that is not your phase.
- The work turns out to need a decision the plan does not make.
- You cannot finish and you are about to stop.

Say what you were doing, what stopped you, and what you need. Ask for the one thing that
unblocks you rather than listing everything you are unsure about — you have a small number of
sends, and a session that messages after every tool call gets cut off. Then end your turn. A
reply wakes you and you carry on from there. Do not sit in a loop waiting, and do not quietly
build something else because the phase you were given is blocked.

**Tell it when you are done**

After the report is written and the PR is open, send the phase number, one line on the
outcome, the PR number, and the report's path.

The orchestrator is idle until that message arrives, so it is the last thing you do and it
is not optional. Send it even when the phase went badly; say so in the line.
