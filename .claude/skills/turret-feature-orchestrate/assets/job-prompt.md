# Job prompt template

Fill every placeholder. The agent starts cold and this is all it knows.

---

You are implementing one phase of the `<slug>` feature. Other sessions own the other phases.

**Start on the feature branch**

You are in your own git worktree. The feature's work lives on `feature/<slug>`, and the
branch you are standing on is not it. Before you read or build anything:

```bash
git fetch origin
git switch -C <slug>-phase-<n> origin/feature/<slug>
```

`-C` creates that branch or resets it, so the same command is right whether this worktree
is new or has already done a phase. Everything you build goes on it. Skip this and you will
rebuild what an earlier phase already did.

**Say what you are on the sidebar**

A person watching the sidebar sees one row per session. Call `mcp__orchestrator__set_status`
before you start reading:

```
mcp__orchestrator__set_status({
  icon: "🔧",
  title: "<slug> phase <n>",
  role: "Implementer",
  task_icon: "📖",
  task: "reading the plan"
})
```

Then call it again with `task` alone as the work moves — "building", "running the proof",
"writing the PR body", "PR open", "blocked, asked the orchestrator". A call naming only `task`
keeps the name and the role you set here. Keep it to a few words; the row gives it one line
and cuts a long one. Nothing else tells the person watching what this session is on.

**Read first**

- `docs/plans/<slug>.md` — the plan. Your phase is **Phase <n>**.
- `docs/plans/memory/<slug>.md` — the feature memory. Facts every session on this feature
  shares. You do not edit this file; see "PR body" below.
- <any file the phase depends on: a design document, a design from an earlier phase>

**Where earlier phases left the code**

<For each phase this one depends on: its number and PR, its File map quoted from the PR body,
and the changed files from `gh pr diff <n> --name-only`. Write "None, this phase builds on
`main` as it stands" when no earlier phase feeds this one.>

Start from these files and the memory's "Files that matter". Search the wider tree for a name
you need that neither of them covers. Each file you read stays in this session's context for
every call after it, so read what the phase needs rather than surveying the tree.

The orchestrator and the sessions that ran earlier phases are searchable: run
`search_conversations` with a distinctive word, and `open_conversation_match` on a match to read
the messages around it. Search them before you work out why something was built the way it was;
the reasoning that never reached the code or a pull request is in their transcripts.

**What to build**

<the phase's "What it builds", quoted from the plan>

**How to approach it**

<the phase's "How to approach it", quoted from the plan. A plan written before that field
existed has none; drop this heading and keep the paragraph below.>

What the phase delivers is fixed. How you build it is yours. The plan's direction says which
way the planner would go: the code to build on, the pattern to follow, the trap they found.
Start from it. The planner read the code before this feature existed, and you are reading it as
it is now, so the files, names and structure are your call. Treat any file or function the
plan does name as a pointer, not a requirement. If the code shows a better route to the same
result, or shows the suggested one won't work, take the better route and say in your PR body
what you did differently and why. Message the orchestrator only when the difference changes
what the phase delivers.

**Proof**

<the phase's proof, quoted from the plan>. This is how you and the orchestrator know the phase
is done. Run it and say what it printed.

**Other phases' work**

<the phase's "Out of scope for this phase", plus anything from the plan's "Not building"
that this phase sits next to>

Deliver what this phase asks for, at the scope the plan intends. Another session builds the
work listed here, or nobody does because the user turned it down. If you build it too, it
collides with that session's pull request. When you find something that needs doing outside
this phase, put it in your PR body, or in `docs/issues/open/` if it is a genuine bug you saw (not
something this phase could not prove: that goes in your PR body), and carry on with the phase. Finish the whole phase, not just the easy part of it. If
some part can't be finished, do the rest and say plainly in your PR body what is missing and
why.

**Finish with a PR**

Commit your work, push your branch, and open a pull request into the feature branch:

```bash
git push -u origin <your branch>
gh pr create --base feature/<slug> --title "<slug> phase <n>: <what>" --body-file <your PR body>
```

Write the body to a file first, under the headings in "PR body" below, and keep that file out of
the repository (`.scratch/` is gitignored).

The orchestrator reads the diff, merges it, and then releases this session, which removes
the worktree. This phase is the whole of your job; the next one goes to a session that does
not exist yet. Leave nothing uncommitted — the removal stops over uncommitted changes, and
work you did not push is work the next phase cannot see.

If the PR shows a conflict because the feature branch moved under you, leave it. The
orchestrator rebases phase branches when it merges them, and it can see the sibling phase you
collided with. Open the PR with its body and send your done message as usual.

**PR body**

The PR body is the phase's record, and nothing else is written for it: no file under
`docs/plans/`. Use these headings, following `docs/plans/README.md`:

- **What was built** — including where you took a different route from the plan, and why
- **What was verified, and how** — the proof, and what it printed
- **What was left undone** — deferred work, and why
- **Bugs found and not fixed**
- **Mechanical friction** — flaky or slow tests, slow builds, anything that cost time
  without being about the feature
- **File map** — the files a later phase will build on, one line each: the path, what it
  holds, and the function, component or type to start from. Include where the phase's tests
  live and the command that runs them. The next phase's session starts with this list in its
  prompt and reads from it instead of searching the tree, so name what it needs and leave out
  files you only touched in passing. Twenty lines at most.
- **Memory suggestions** — what you would add to the feature memory, and why the next
  phase would otherwise rediscover it. Schema that settled differently from the plan,
  invariants that turned out to matter, files whose importance was not obvious. No code,
  and nothing about what you did — that is the rest of this body. The next phase runs in
  a session that has none of your context, so anything it needs and cannot read off the
  branch has to come through here. Ask only for what every later phase must have pushed to it
  (a schema, an invariant). The reasoning behind your choices stays in this session's
  transcript, where a later phase finds it with `search_conversations`.

**Work unattended**

Nobody is watching this session, and you have no tool for asking a user anything — the spawn
removed it. Bias toward working without stopping for clarifying questions. The plan has settled
what the feature is, and the implementation choices are yours to make. When you would normally
pause to check, make the reasonable call, keep going, and say what you decided in your PR body.
When you are genuinely blocked, message the orchestrator, which is the one thing that can
answer you.

**Talking to the orchestrator**

The session that started you is the orchestrator, and you can message it at any point with
`mcp__orchestrator__send_parent_message`, which takes the message alone. A spawned session's
`send_message` reaches only the sessions below it, so it does not reach the orchestrator.

Message it as soon as you are stuck. It holds the whole plan, you hold one phase, and the
thing blocking you is usually something it can answer in a sentence or decide on your behalf.
Worth a message:

- The plan tells you to build against something that is not there, or that works so
  differently from how the plan describes it that the phase can't deliver what it promises.
- A dependency you were told had landed has not.
- The proof cannot be run as written, or fails for a reason that is not your phase.
- The work turns out to need a decision the plan does not make.
- You cannot finish and you are about to stop.

Say what you were doing, what stopped you, and what you need. Ask for the one thing that
unblocks you rather than listing everything you are unsure about — you have a small number of
sends, and a session that messages after every tool call gets cut off. Then end your turn. A
reply wakes you and you carry on from there. Do not sit in a loop waiting, and do not quietly
build something else because the phase you were given is blocked.

**Tell it when you are done**

After the PR is open, send the phase number, one line on the outcome, and the PR number.

The orchestrator is idle until that message arrives, so it is the last thing you do and it
is not optional. Send it even when the phase went badly; say so in the line.
