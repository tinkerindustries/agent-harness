Web UI design pass

Flat HTML, no build, no JavaScript. Every collapsible is a <details> and every token name is shadcn/ui's, so the mocks translate to components rather than needing a re-decision. Open the files directly in a browser.

Mocks

sessions.html — the main page

In-flight sessions become collapsible cards showing the live plan; finished sessions stay a dense table. OK splits into DONE, GAVE UP and STOPPED.

transcript.html — the session page

A sticky timeline rail grouped by plan item, one card per sub-turn, a density toggle, and tool calls that show their target instead of their JSON.

settings.html — the settings screen

The registry as a list of disclosures: closed is key, value and description; open is the bounds and the write. Only the exceptions are badged, and a closed set becomes a segmented control.

components.html — vocabulary and components

The outcome-to-badge mapping with the store fields each one reads, the colour tokens in both themes, and which shadcn component each mock class becomes.

What the mocks are measured against

  • The live session sess-f93b37beb37098b5637832e829c37d92: 142 sub-turns, 16:31, 99.3% cache hit, $0.0838. Its page is 86,674 pixels tall and mounts 974 block elements. The plan, the numbers and the diffs in the mocks are that session's.
  • Every session in the current list shows a green OK, including the ones that gave up. The store distinguishes them already — see components.html.
  • The settings mock is the registry itself — 27 entries in five groups, four of them overridden on this installation. The bounds and the closed set it draws are on settings.Descriptor and not yet on the wire.
  • Nothing proposed here starts, steers or stops a run. The one write is PUT/DELETE /api/settings/{key}, which stops at the settings table; everywhere else the server stays GET and HEAD.
