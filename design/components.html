Session outcome vocabulary

The store already distinguishes these outcomes. The current UI renders every one of the first three as a green OK, which is why a session list of runs that gave up, stopped early, or finished cleanly all read as success.

Badge store status run_finished.reason run_finished.status What happened
RUNNING running — — In flight. The session list groups these above the table and gives them the collapsible plan card.
DONE ok complete done The model called Complete(status: "done"). This is the only outcome that means the model claims the task is finished.
GAVE UP ok complete gave_up The model called Complete(status: "gave_up"). It stopped deliberately without finishing. The summary says why.
STOPPED ok no_tool_calls absent The model answered in prose and called no tool. Normal for a question; suspicious for a task. Thinking mode cannot be forced to call Complete (docs/DESIGN.md §4.6), so this is not an error.
MAX TURNS max_turns max_sub_turns absent The loop hit the sub-turn ceiling. Whatever was in progress is unfinished.
FAILED failed — — An error event ended the run. The message is the last block in the transcript.
TIMEOUT timeout — — The run exceeded its wall-clock budget.
CANCELLED cancelled — — The context was cancelled, usually a shutdown.
COMPACTED compacted — — A superseded row. Hidden from the list by default; reachable from the successor session's header.

Where each field comes from

transcript screen

Already has everything. The run_finished block carries reason and status, so DONE / GAVE UP / STOPPED needs no backend change on this screen.

session list

Needs one new field. hub.SessionState carries only status; add complete_status alongside it, persisted on store.Session so it survives a restart.

live plan

Needs a second new field. Todos are parsed client-side from the latest TodoWrite arguments, which the list feed never sees. Publish the plan on SessionState, or serve it from GET /api/sessions/{id}/plan.

settings screen

Needs three fields it already has in Go. Min, Max and Allowed are on settings.Descriptor and none of them are on settingEntry, so the browser cannot show a bound the CLI shows, and cannot know model.effort is a closed set. Everything else on that screen is already served.

Setting state vocabulary

The settings screen badges the exceptions only. A row at its registry default carries no badge at all — twenty-three default badges on a 27-row screen say nothing, and the value column already carries the state by weight.

Badge GET /api/settings What it means
— set: false, non-secret Nothing stored; the registry default applies. Unbadged, value muted. The common case.
OVERRIDE override: true A stored value that differs from the default. Value at full weight, and the open row names the default and offers to reset to it.
SET secret: true, set: true A credential is stored. The value column shows the server's mask; a secret's default is the empty string, so "override" would be technically true and say nothing.
NOT SET secret: true, set: false A missing credential. The open row names what stops working — for google.api_key, ReviewScreenshot and nothing else.
restart restart: true Read once at startup or baked into a JetStream stream. Every flagged key is in the "Requires a restart" group today, so the group heading carries it and the row does not; the badge is here for a flagged key that ever lands in another group.

Tool glyphs

One monospace letter per tool, coloured by family, so the timeline rail shows the shape of a sub-turn without opening it. Writes are green, shell is blue, a failed result overrides with red.
