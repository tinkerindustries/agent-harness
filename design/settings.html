Settings

The registry, rendered. Every row is one entry in internal/settings — its type, default, bounds and description come from there, and so does the validation, so a value this screen rejects is rejected identically by harness config set. This screen is the browser's only write and it stops at the settings table: nothing here starts, steers or stops a run.

What is proposed here

  • Reading is the default state; writing is an act. The current screen renders a text input and two buttons on all 27 rows at once — 27 fields and 54 buttons in the tab order for a screen where a session typically changes nothing. Each row becomes a <details> whose closed state is key, value and description, and whose open state carries the write controls.
  • The value column carries the state, not a badge on every row. A stored value takes full weight, a default stays muted, and only the exceptions — override, not set — are badged. Twenty-three default badges tell an operator nothing.
  • A closed set is a segmented control. model.effort accepts exactly low, high, max; the registry knows that, so the screen should not make you discover it through a 400.
  • Bounds are shown before the write, not after it. Validation stays in Go — the screen never re-implements a rule — but showing 1 – 1000000 beside the field turns most rejections into non-events. When one does happen, the server's message lands under the field it belongs to, which the current screen already does.
  • An unset credential says what stops working. The registry default for an API key is the empty string, so the current "not set — default  applies" renders with a hole in it and understates the case. google.api_key unset means ReviewScreenshot fails and nothing else changes; that is the sentence worth writing.
  • The restart caveat moves to the group. Every restart-flagged key is in the "Requires a restart" group today, so the heading and one notice carry it. The per-row restart badge stays in the vocabulary for a flagged key that ever lands in another group.
  • The secret rule is stated on the screen. Masked to four characters, no reveal parameter, harness config get -reveal at a terminal if you need the value. An operator who cannot see the rule assumes the field is broken.

What the API needs

  • min, max and allowed on the GET /api/settings payload. All three are already on settings.Descriptor and none of them are serialised (internal/httpapi/server.go, settingEntry). Without them the range hints and the segmented control cannot be drawn, and the CLI shows bounds the screen cannot. Nothing else on this page needs a backend change.
  • Optional, and only a nicety: a unit flag for the byte-valued integers, so 4194304 can be glossed as 4 MiB without the screen pattern-matching on the description.

What stays true

  • Writes are PUT/DELETE /api/settings/{key} and stop at the settings table. No control here reaches a run, and the run surface stays GET-only (docs/DESIGN.md §4.2).
  • Validation lives in the registry and runs in Go on every path, so harness config set, the PUT, and this screen reject the same value with the same message.
  • The screen re-fetches after a write rather than guessing at the new display value — the server owns the mask.
