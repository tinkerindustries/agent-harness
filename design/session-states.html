Session page states

The resting state of each session page is drawn in its own file — session-chat.html for a run a person started, session-watch.html for a run an agent started. Both are fixed-height app shells, so they can show exactly one state each. These are the rest.

Interactive · before the first message

POST /api/runs creates the run with no prompt: the operator types the first message into the same box every later message goes into (docs/RUN-CONTROL.md, "The frontend"). So the empty state is not an error page — it is the composer with the stream still empty, and one line saying what happens when you press enter.

state: claimed, zero sub-turns

Interactive · the three states of a sent message

A steer is accepted, then delivered — two events, two states, and the gap between them is the diagnosis when a run is wedged (docs/RUN-CONTROL.md, "Two event kinds, not one"). A message that sat pending for four minutes is telling you something, so the pending state names what it is waiting on and counts up rather than showing an indeterminate spinner.

Both pages · stopping

Stop is behind a confirmation because a run you cannot get back is hard to reverse, and it reports an acceptance rather than an outcome: between the 202 and the terminal event the control says stopping…, because the loop finishes its current tool call first (docs/RUN-CONTROL.md, "Stopping").

confirmation, in place — not a modal over the transcript
Stop this run? It is 4m 12s in, mid scripts/test.sh. The work it has done stays in the workspace.

Stopping… waiting for the current tool call to return. The run ends at the next boundary.

Interactive · the run is over

Steering a finished run would sit in the log forever, unapplied and unexplained, and the endpoint refuses it anyway — so the composer is removed rather than disabled. A greyed-out box invites you to hunt for the way to enable it; a sentence and the action you actually want does not.

Watching · the result the parent gets back

For a run another agent launched, the result payload is the point — it is what gets returned to the caller. It renders at the end of the stream, where the run actually ended, rather than in a panel off to one side, and it carries a copy control because the next thing a person does with it is paste it somewhere.
