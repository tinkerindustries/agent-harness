# Session review — sess-e78152d6349949dff772ecfa6d0297ec

A vision-path run: capture the production session list four ways, review it with
Gemini, write the advice up, implement the fixes, confirm them. It produced a
116-line review document, two CSS changes, five green check commands and draft
PR #115 — and one of those two changes is a judgement call that no reviewer
asked for and that ships broken at phone width. The run was launched as a test
of whether flash can do a design pass; the honest verdict is that it was a good
*run* and a poor *design pass*, and the gap between those two sentences is the
whole finding. Nothing mechanical failed. The model's referee work was excellent
and independently checks out. Its one original design idea is the defect.

## Mechanical failures

**None.** Three candidates were checked against the code and all three are the
system working as designed:

- **`mode` refused on a follow-up call** (11): `a follow-up call takes no mode:
  this conversation is in review mode, fixed when it started`. The parameter's
  own description ends "Fixed when the conversation starts." The model did not
  read it. Cost: one call slot, and a fresh conversation at 12 ($0.0274) that
  lost the first thread's context. Behavioural, cheap.
- **The four-image cap discovered at runtime** (61): `ReviewScreenshot accepts
  at most 4 images, got 6`. `internal/tools/definitions.go:151` documents why no
  number appears in the description — the caps are settings, the text is in the
  frozen request head, and a per-installation number would cost the whole prompt
  cache. Discovery-by-refusal is the intended contract. Cost: one sub-turn
  ($0.0005), recovered immediately by splitting into two calls.
- **Two `Complete` rejections** (79, 80): first missing `branch` and `error`,
  then an extra `pulled_request_url` alongside the correct key. The opening
  message states the exact shape. Cost: 2 sub-turns, $0.0017. Model slips, and
  the validator did precisely its job — the third call was clean.

The `repeated-call` flag at 58 is a false positive: 56 and 58 are byte-identical
`node scratch/swap-review.mjs` invocations with an `Edit` between them fixing
`require` → `import`. Correct behaviour, not a loop.

Cache held at 98.5% with no churn. No retries, no denials, no truncation, no
stall.

## The shipped defect

`web/src/styles.css`, the ≤560px block:

```css
.table-scroll .session-table td { text-align: left; }          /* 0,2,1 */
```

is written to undo the new desktop rule inside the phone stacked cards. It loses
on specificity to

```css
.table-scroll .session-table td:nth-child(3) { text-align: right; }   /* 0,3,1 */
```

Media queries add no specificity, so source order never comes into it. Those
four cells carry `flex: 1 1 40%` at that width, so they are wider than their
content and the alignment is visible: the figure *and* its uppercase `::before`
caption sit flush right inside a card whose title is flush left. Reproduced at
390px with just those rules in isolation — the value stays hard against the box
edge.

The model wrote the reset deliberately and reasoned about it twice (30, 33: "the
phone stacked cards reset to left alignment below"). It never questioned whether
the reset would win. There is no evidence it considered specificity at all.

**Why nothing caught it.** Every other claim in this run was verified against a
picture. This one could not be:

- The local stack has no sessions, so the phone table renders the empty state.
  The model said so, in the document and the report, before the fact.
- `scripts/layout-check.sh` passed at 390px, but it only reports horizontal
  overflow and console errors — right-aligned text overflows nothing.
- The CSS-swap harness the model built *could* have seen it. `swap-elements.mjs`
  (59) captures six before/after element shots and already takes a per-shot
  `width`. It spent its two phone slots on `.topnav` — where **no change was
  intended** — and never captured `.table-scroll` at 390px, where the reset was
  the entire point. One extra pair in that array, three lines, would have shown
  it.

That is the sharpest lesson in the session: the run verified the places it had
changed nothing, and skipped the one place its change needed a reset.

## Where the model did well

Reported with the same rigour as the defect, because these are what a prompt
change could destroy. Each was checked independently.

- **Refused a high-confidence false positive** (11–13). Gemini's first pass
  returned three findings, two of them the same claim: the phone table's numeric
  columns are "entirely missing". The model suspected the 800px fold on a
  6256px document, spent a `describe` call to enumerate what was actually in
  frame, saw the first row cut off mid-subtitle, and confirmed against a
  full-page capture. It then recorded the finding as an artifact rather than
  fixing a bug that did not exist. The `Observed:` line it used to do this is
  the fix recommended by [`vision-path-2026-08-14.md`](vision-path-2026-08-14.md);
  this run is evidence that it shipped and works.
- **Overrode the reviewer with the codebase** (15). Gemini flagged sub-44px
  touch targets. The model found `styles.css:203` — "Control heights. Density is
  the point: nothing in the harness is 44px" — and at 31 sharpened it further:
  WCAG 2.5.8 (AA) requires 24px, 44px is HIG/AAA, and every target clears 24px.
  It recorded the reasoning rather than obeying generic web convention.
- **Computed contrast by hand and was right** (21). Gemini called the dark
  RUNNING badge "extremely low contrast… barely legible". The model converted
  `hsl(217 91% 68%)` and `hsl(217 60% 15%)` to sRGB, took relative luminance,
  and got 5.79:1 — passing AA. I recomputed it; the arithmetic is correct. It
  discarded the claim.
- **Caught a vision measurement error by re-measuring** (17→20). Gemini reported
  the in-flight card's badge at x=70 and its text block at x=54 — a real-sounding
  misalignment. The model reasoned from `.run-summary`'s padding that they must
  share an x, captured `.run-card` alone at full resolution, and got 46/46/46.
- **Built a harness the brief never asked for** (55–60). Faced with "the local
  stack has no data", it wrote a Playwright script that loads *production's* page
  and intercepts the CSS and woff2 requests to serve its own branch's bundle —
  production's markup and data, its own stylesheet. That is the only way an
  after-with-data comparison existed at all, and it is genuinely inventive.
- **Scoped the selector correctly** (32–33). It checked whether the eval screens
  reuse `.session-table` (they do), found they sit in `.eval-table-scroll`, and
  scoped its rule to `.table-scroll` so `nth-child(3)` could not hit the eval
  table's unrelated "Compared" column.
- **Re-ran the Go suite to get an honest exit code** (68). The first run's
  `tail` swallowed the status. Rather than infer success from "ok" lines, it
  re-ran the whole suite redirected to a file and captured `exit=0`. Two minutes
  spent on not overstating a result.
- **Left production alone.** Every touch was a GET, including the swap renders.
  Verified at 76: prod still 200, no `prod-ui-review` containers, slot 2 freed.

## Where the model struggled

**One thing, and it is the interesting one: it cannot originate a design
judgement, only referee one.**

Of the two findings that shipped, one was *filtered* and one was *originated*.

The placeholder truncation (20) came from Gemini looking at a close-up of the
nav; the model's job was to decide it was real, which it did well. Everything
else Gemini offered, the model correctly threw away. As a referee it is close to
excellent — four claims examined, three rejected with reasoning that holds up
under independent check.

The right-aligned numeric columns are the one finding the model produced by
itself, with no image behind it. It arrived from a rule — *numbers in a data
table are right-aligned* — and the supporting evidence it gathered was textual,
not visual: it grepped `text-align: right` and found the rail's turn numbers,
the diff gutter, the settings values. All true, and all in fixed-width columns
where the rule earns its keep. It could not see that the table's four columns
are narrow and intrinsically sized, that the product is otherwise uniformly
left-aligned, or that the in-flight card directly above renders the same two
figures left. It is design-by-citation, which is what is left when you cannot
see the page.

The transcript is unusually candid about the model's own uncertainty. It
revisits the decision at 24, 26, 29, 30, 32 and 33 — "I keep going back and
forth", "I'm 50/50 on this one", "let me reconsider ONE more time whether to
include the right-alignment change at all" — and ships it anyway. What tips it
is not evidence. It is volume:

> 30: "That's thin for 'the five with the largest visual payoff'."
> 32: "Hmm — only two."

**That sentence is the brief's fault, not the model's.** "Implement the five
with the largest visual payoff" was written as a ceiling and read as a target.
The model spent roughly ten sub-turns hunting for a second finding it did not
believe in, and shipped it to avoid a thin deliverable.

## What it missed

- **The specificity of its own reset** (40) — the shipped defect above.
- **The pairing of its verification to its change** (59). It chose the phone
  `.topnav` for the phone before/after pair and asked "no change was intended
  there — check for unintended damage". Sound instinct, wrong element: the
  change it had made at phone width was in the table.
- **That its two findings sit in different classes of evidence.** The document
  presents both as findings from the review. One came from a picture; one came
  from a convention the reviewers never raised. A reader of the document cannot
  tell them apart, and a reviewer of PR #115 would want to.

## Where it lost the thread

Nowhere. At 81 sub-turns this session is too short for drift, and the notes bear
that out: no file re-read it had already read, no re-run of a check whose result
it held, no constraint restated in weaker terms. The plan written at sub-turn 2
matches what happened, item for item, with all eight completed and supported by
the transcript.

## What this run does and does not tell you about the model

It is tempting to read this as "flash cannot design". The evidence does not
support that claim cleanly, because **flash never saw the page**. Every visual
observation in these 81 sub-turns came from Gemini; DeepSeek's contribution was
choosing what to ask and judging what came back, and it did both well.

What the run does show, narrowly:

1. **As a referee of a vision model's claims, flash is strong** — three of four
   rejections correct, each backed by the codebase or by arithmetic I could
   re-derive.
2. **As an originator of design judgement, it falls back on textbook rules**,
   because rules are the only design input available to something that cannot
   see. That is where the net-negative change came from.
3. **The page was genuinely clean**, and that is the largest single reason the
   output looks thin. This is the same page the repo's own vision-path review
   already found `0 findings` on, correctly, and it had just had three dedicated
   phone/mobile-layout passes (#108, #111, #114) before v0.34.0. Pointing a
   design review at it was always going to return little.

The one true finding — the clipped placeholder — came from an **element-level
close-up of `.topnav`** (19→20), not from any of the four full-viewport captures
the brief mandated. Those four produced exactly one high-confidence finding and
it was false, generated by the 800px fold. The full-page follow-ups returned
nothing. This is the third consecutive review to reach the same conclusion by a
different route: **the vision path pays when it is aimed at one control, and
does not pay when aimed at a page.**

## Ranked fixes

1. **Prompt (mine, immediate).** Delete finding-count language from the vision
   brief. "Implement the findings you judged real; if that is zero, say so and
   stop" — the current "five with the largest visual payoff" manufactured the
   one change that should not have shipped. Highest impact of anything here.
2. **Prompt (mine).** Add the verification rule this session needed: *if you
   wrote a media-query override, capture that viewport after the change.* Three
   extra lines in `swap-elements.mjs` would have caught the defect.
3. **Prompt (mine).** Require findings to be labelled by evidence class —
   *seen in capture X* versus *inferred from convention* — so a reviewer of the
   PR can weight them differently. The model's document does not distinguish
   them and neither did its report.
4. **Prompt / skill (`deepseek-flash-task` or a vision-specific one).** Lead the
   capture plan with element close-ups and use the full-page shot only to decide
   *which* elements to close up on. Costed above: the page-level captures in this
   run returned one false positive for ~$0.20.
5. **Tool description (`internal/tools/definitions.go`).** `ReviewScreenshot`
   already warns that a full-page capture is downscaled. Consider adding the
   converse in the same sentence — that a *viewport* capture of a long document
   silently omits everything below the fold, and a finding of the form "X is
   missing" from one is a fold artifact until a full-page capture says otherwise.
   That single failure cost ~$0.10 and six sub-turns to unwind here, and the
   same trap appears in the earlier vision-path review.
6. **Nothing to fix in the harness.** Recorded explicitly so the next reader does
   not go looking: all three mechanical candidates were the documented contract.
