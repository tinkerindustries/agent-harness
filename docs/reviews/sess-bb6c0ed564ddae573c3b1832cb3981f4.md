# Session review — sess-bb6c0ed564ddae573c3b1832cb3981f4

Phase 5 of the session-pages plan: drive the two new session pages against a real
streaming run, and repair what that exposes. The run did the work and did it
well — it stood up an isolated stack against a live API key, drove both pages
through the browser, found and fixed four genuine product bugs with tests, wrote
the TESTING.md section, and pushed three commits and a PR. Then it spent its
last eleven sub-turns failing to call `Complete`, misdiagnosed its own malformed
tool call as a harness serialization fault, and ended the run on `no_tool_calls`
asserting a bug in the harness that does not exist. The engineering is excellent;
the last four minutes put a false claim into the permanent record.

## Mechanical failures

### 1. None — the headline failure is the model's, not the harness's

The flagged `error-loop` at sub-turns 348–358 is eleven consecutive `Complete`
calls, each rejected with:

```
result does not match the required schema:
- result: expected object, got null
```

The run concluded, and stated in its final answer, that "the `result` parameter
is being nulled by the harness on every attempt … a serialization failure on the
environment's side that I cannot work around from inside the session."

That is wrong. Every one of the eleven calls parses as valid JSON, and every one
carries the same key set:

```
['branch', 'deferred', 'error', 'files_changed', 'status', 'summary', 'verification']
```

There is no `result` key in any of them. `Complete` takes exactly three
parameters — `summary`, `result`, `status` (`internal/tools/definitions.go:156`)
— and validates `args.Result` against the run's schema
(`internal/tools/complete.go:31`). The model put the six schema fields
(`summary`, `deferred`, `verification`, `branch`, `files_changed`, `error`) at
the *top level* of the call alongside `status`, where the tool ignores them,
instead of nesting them inside `result`. `args.Result` was therefore genuinely
absent, and the harness's error message was precisely accurate.

Across eight diagnostic attempts the model varied only the payload *size*
(14467 → 4819 chars) and never the *shape*. It explicitly considered and
rejected the correct hypothesis at sub-turn 354 — "maybe I need to pass result
as a JSON string? No — the schema says type object means the argument itself
should be an object" — which is true, and would have been the right conclusion
if it had ever looked at whether it was passing an argument named `result` at
all. It never re-read the tool definition it had been given.

**Cost:** 11 sub-turns, $0.0214 (7.0% of the run), 207s of model time (10.6%),
31,404 completion tokens (17.6% of everything the model wrote all session). The
run then ended on `no_tool_calls` with no validated result, so the requester got
prose instead of the machine-readable payload the schema existed to guarantee.

Confirmed against the code, not inferred.

### 2. `--include` is unsupported by the container's busybox grep

Sub-turns 25 and 29. `grep -rn ... --include="*.go"` prints a usage banner
instead of matching. At sub-turn 29 the model's own `2>/dev/null` swallowed the
banner, so it read the empty output as "no matches" for a repo-wide search for
`DEEPSEEK_API_KEY`. It recovered at sub-turn 30 by grepping differently, and the
true answer happened to also be "no matches", so nothing downstream broke. It
recurred at sub-turns 169–171.

Confirmed by running the same commands inside the prod harness container: busybox
supports `\|` alternation and `-A`, and rejects only `--include`.

**Cost:** four wasted round trips. Low impact, but the silent-empty-result shape
is the dangerous part — a suppressed usage banner is indistinguishable from a
genuine no-match.

### 3. The workspace path cannot be a docker bind-mount source

Sub-turn 53. `docker compose up` failed with `mounts denied: the path
/workspaces/sess-…/workspaces is not shared from the host`. A
session's workspace lives under `/workspaces` inside the agent container, which
is not a Docker Desktop shared path, so any compose stack the session brings up
cannot bind-mount anything under it. Compounding it, the agent container cannot
reach *any* docker-published host port (sub-turn 58: `127.0.0.1:8701` refused
while the container reported healthy) and had to find the harness container's
bridge IP to drive the UI at all.

Both are environment facts rather than harness bugs, and the brief warned about
the second for the test broker. The model worked around both correctly. Worth
recording because any future session asked to stand up a stack will hit them
again, and sub-turn 55 cost 37s of reasoning and ~9KB of thinking to re-derive.

### 4. A GitHub PAT was written to the event log in clear text

Sub-turn 71. The model wrote `GITHUB_TOKEN` into `.env` with `printf` and then
ran `head -2 .env`, putting the full `github_pat_…` value into a `tool_result`
event. `harness config` masks secrets by design (`cmd/harness/config.go`
`maskSecret`), and the event log has no equivalent guard. Not this run's fault —
the token was in its environment and it needed it in the container — but the
transcript is now a credential store, and the HTTP API serves transcripts.

Hypothesis, not confirmed: I have not checked whether anything else redacts on
the read path.

## Where the model struggled

**Only in the last eleven sub-turns, and only in one way: it stopped checking
its own inputs.** Every earlier diagnosis in the session was disciplined — form
hypotheses, design an experiment that separates them, run it. The `Complete`
loop is the one place it formed a single hypothesis (payload size), never
generated a competing one about its own call shape, and treated eleven identical
error messages as evidence about the environment rather than as evidence that
the thing it kept doing was constant.

The tell is in its own reasoning at sub-turn 353: "This suggests the `result`
parameter itself is being dropped somewhere in the pipeline." The word
"dropped" presumes it was sent. It never verified that presumption, though the
tool schema was one Read away and the arguments it had just constructed were in
front of it.

## Where the model did well

This is the larger part of the session and it is genuinely strong.

**It validated its foundation before building on it.** Sub-turns 35–36: rather
than assume the `DEEPSEEK_API_KEY` in its environment was real, it called
`https://api.deepseek.com/models` and got both model ids back. Sub-turns 69–71:
it predicted that a private-repo clone would fail for lack of `GITHUB_TOKEN` in
the container's `env_file` and fixed it *before* starting a run that would have
died on it.

**It separated tooling error from product bug.** The first browser run ended with
no task. Instead of filing a bug, it named two hypotheses — the text never
entered the textarea, or Enter did not fire — and designed run #2 to
discriminate, verifying `textarea.value.length == 430` before pressing Enter
(sub-turns 91–98). Same discipline at sub-turn 242, where a failed jump-pill
click turned out to be its own stale ref rather than a product fault, and it said
so.

**It read a subtle log format correctly.** Sub-turns 110–111: it reconstructed
the steer race purely from commit timestamps, correctly accounting for the fact
that a sub-turn's events are all stamped at commit time — so `turn_started`
carries the time the model *finished*. It derived that sub-turn 3's request began
at ~38.1s from `elapsed_ms 6821` and a commit at 44.949, and concluded
`pickUpSteers` had run before the steer existed. That is a sharper reading of
this log format than the harness's own review tooling manages; my first pass at
`fetch_session.py` made exactly the error it avoided and reported a fabricated
37s "harness stall".

**It scoped changes before making them.** Before adding the first-steer wait it
checked every caller that could pass an empty prompt (MCP validates non-empty at
`launch.go:131`, publish requires a positional, subagents always have one) and
confirmed the wait would be scoped to `POST /api/runs` alone, then checked that
stop and deadline both land correctly in `pool.classify` (sub-turns 119–122).

**It found four real bugs the four previous phases had missed**, each with a
test:

1. A browser-started run sends `Task:` with nothing after it, the model asks what
   to do, and the run ends on `no_tool_calls` in ~15s — before an operator can
   type. The design (`session-states.html` "claimed, zero sub-turns") says
   nothing is sent until the first message. Fixed with `waitForFirstSteer`;
   verified live at sub-turn 184, where the run sat on one event for 10s.
2. A steer landing while the final sub-turn is in flight is never applied, and
   the page renders "pending · waiting for the next sub-turn boundary" above a
   finished run forever. Fixed on the display side after arguing itself out of
   the backend change (sub-turns 201–208) — the reasoning about why not to extend
   a completed run is the best judgement call in the session.
3. A browser stop leaves the session row `running` with no `finished_at` — the
   queue result says `cancelled`, the page stays stuck on RUNNING. Root-caused to
   `fail()` doing its terminal bookkeeping through the run's own cancelled
   context (sub-turns 265–275). Fixed with a fresh bounded context and the right
   terminal status.
4. Both phase-4 gaps: `PendingTool.startedAt` for the footer's tool age, and the
   launching agent's instruction as its own `.msg-user` block.

**It correctly declined to fix a fifth.** Sub-turns 221–224: it discovered that
reasoning and content deltas are committed as one batch at sub-turn end, so the
design's live "Thinking… 3.1s" state is unreachable on a real run — only Bash
stdout streams. It traced this to the deliberate atomic-commit decision
(DESIGN.md §4.5), judged that changing it was a backend redesign rather than a
repair, and recorded it as observed behaviour. That restraint is right, and the
finding is worth someone's attention independently.

## What it missed

  the opening message it had already read.
- **`docs/TOOLS.md`.** CLAUDE.md names it as the tool contract reference. At
  sub-turn 73 the model grepped it for `"permission mode\|PermissionMode\|readonly"`,
  got nothing (the file writes "Permission is a policy" and "read-only"), and
  abandoned the doc, reconstructing the permission model from
  `internal/tools/policy.go` over sub-turns 74–77. It got the right answer, so
  the cost was five sub-turns — but the habit of grepping a document for a
  guessed phrase instead of reading it is what put it one Read away from the
  `Complete` contract and never closed the gap.
- **Its own plan.** Items 5 and 6 ("Fix gap 1", "Fix gap 2") are still `pending`
  in the session row while 7 through 10 are `completed`. Both were in fact done
  (sub-turns 140–168). The plan is a status display for a watching operator, and
  it says two fixes were skipped when they were not.

## Where it lost the thread

Very little, for 359 sub-turns. Two instances:

- **Sub-turn 177 re-derived what sub-turn 25 established.** It hit busybox's
  missing `--include` at sub-turn 25, again at 29, and again at 169–171 — 144
  sub-turns after the first encounter — before switching to `find | xargs grep`.
  The lesson never got written down anywhere it would see again.
- **The plan drift above** is the clearest case: task 7 ("Fix findings from the
  live runs") was marked in-progress at sub-turn 128 and the model worked
  continuously from there, never returning to close 5 and 6, which it had
  actually completed in between.

Against that, the durable thing is what did *not* drift: the model held the
brief's constraints — do not disturb the host stacks, tear down the worktree,
report honestly what could not be run — across the whole session, and acted on
them at sub-turn 55 (choosing a scratch directory over the host's real worktree
registry) and at the teardown.

## Ranked fixes

1. **[Prompt / tool description] Make `Complete`'s result nesting impossible to
   get wrong.** This cost 7% of the run and produced a false bug report. Two
   cheap changes, either of which would have prevented it: have
   `RenderOpeningMessage` show a worked example of the call shape
   (`Complete(status=…, summary=…, result={…})`) rather than only the bare JSON
   Schema, and have `execComplete` detect the specific failure — schema-required
   top-level keys present as sibling arguments while `result` is null — and say
   so: "result is null, but I see `summary`, `branch`, `files_changed` as
   top-level arguments; the schema fields go inside `result`". A validator that
   names the likely mistake ends this loop at attempt one.
   Files: `internal/session/prompt.go`, `internal/tools/complete.go`.

2. **[Mechanical] Stop the `Complete` retry loop from being unbounded.** Eleven
   identical rejections is the loop working as designed and the model working as
   designed, producing a pathological result together. After N consecutive
   `Complete` failures with the same validation error, the loop should end the
   run with that error as the terminal state rather than letting the model spend
   its budget rephrasing. This is the generic version of finding 1 and protects
   against the next schema the model mis-shapes.
   File: `internal/session/runner.go`.

3. **[Mechanical] Redact secrets on the transcript read path.** A `github_pat_`
   value is sitting in this session's event log in clear text, and the HTTP API
   serves it. The store's masking exists for `harness config`; the events
   endpoint has nothing equivalent.
   Files: `internal/httpapi`, `internal/store`.

4. **[Environment] Record the container's shell limits where a session will see
   them.** `--include` is unsupported, `curl` is absent, and a suppressed usage
   banner reads as a no-match. Three sub-turns were lost to this across the
   session and the same trap is waiting for every future run. One line in the
   opening message or in CLAUDE.md's commands table.

5. **[Investigate] The live-streaming states may be unreachable.** The model's
   sub-turn 221–224 finding — reasoning and content deltas commit in one batch at
   sub-turn end, so `LiveTurn`'s "Thinking… 3.1s" never renders on a real run —
   deserves a decision rather than a note. Either the design's live state is
   wrong about what the backend can deliver, or the commit granularity should
   change. This is a diagnosis, not a fix: it was correctly deferred here.
   Files: `internal/session/turn.go`, `web/src/components/turns/LiveTurn.tsx`,
   `docs/DESIGN.md` §4.5.
